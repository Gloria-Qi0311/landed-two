### Diff (a) — Scope-cut protocol for oversize issues (new §2 step 2b)

**Triggered by**: `stop_condition_hit::scope_too_large_for_one_pr` (cumulative: 1; below threshold but high-cost failure mode; pattern self-discovered + applied successfully on both #29 + #30).

```diff
--- a/SKILL.md (§2, between steps 2 and 3)
+++ b/SKILL.md
@@
    If they diverge: `git stash -u` → `checkout main` → `pull --ff-only` → `branch -D feat/<name>`
    → `checkout -b feat/<name>` → `stash pop`.
+
+2b. **Scope-check the issue before implementing.** Issues filed for human engineers
+    ("rewrite the popup", "port the X module") are often sized for internal chunking the human
+    would do mid-task. For /devloop the chunking must happen UP FRONT so each PR is reviewable.
+    Before writing code: read the existing implementation the issue is replacing; if it's >~500
+    LOC OR has ≥3 distinct user-visible features OR will produce a diff >~800 LOC, **scope-cut**:
+    ship a scaffold-only first PR (foundation + minimum-viable wiring; existing code stays as
+    reference) and file follow-up issues for each deferred feature with concrete scope. Mark
+    the scope-cut explicitly in the PR title (e.g. "(partial: bundler + sign-in shell only)")
+    and body (what's IN, what's deferred + to which follow-up issue #).
+
+    A scope cut is NOT a rollback when: (1) the shipped scaffold is complete + runnable + tested,
+    (2) net product capability does not regress (old code stays on disk as reference until
+    follow-ups ship), (3) follow-ups are filed with concrete scope before the next task starts.
+    If any of those fail, it IS a rollback — `stop_condition_hit` and ask the user.
 3. **Implement** in small steps. Read the surrounding code first; match its conventions, comment
    density, naming, idioms.
```

**Anti-pattern check**: PASS — operational; strengthens scope discipline.
